# First concurrent Wi-Fi video and microphone proof —2026-11-15

Both media streams now reach the PC over the home network at the same time.
This bounded trial used native RTSP for video and CammyOS's authenticated,
owner-scoped HTTP PCM endpoint for microphone. No USB media transport, TF
recording, camera mode change, new native app or internal firmware write was used.
PC USB remained connected for setup and metadata checks; a physical power-only
charger demonstration and unattended reboot/startup are not established here.

## Setup and exact scope

The camera runs the existing0.4.0 portal with the RAM-only compatibility
correction documented in [0.4.1](RELEASE-0.4.1.md). During this trial the card still held uncorrected0.4.0; the subsequent
[0.4.1 card update](RELEASE-0.4.1.md) is verified, with camera boot acceptance pending.
Adam opened the native CammyOS/AT-M105 Wi-Fi screen. This created native8554
listeners on both the home and hotspot addresses, while the radio remained
associated with <home-wifi>. The UI changed wlan0's interface address to192.168.10.1.
USB setup verified the same boot, the new stock `udhcpd` process identity, and
the existing runtime DHCP client's PID/start time/executable. It terminated only
that DHCP server and sent USR1 to the owned client, restoring<camera-ip>.
No adapter mode change or native app restart was performed.

The SDK acquired a60s lease, started the stock event session, and decoded native
RTSP video into160×90 grayscale monitor frames at a requested5Hz. The microphone
request began after the first decoded video frame and read20s of raw mono16kHz
S16_LE PCM. The two transports overlapped while both sources were running.
This is live delivery, not downloading a completed clip.

## Stop and desktop state

Closing the microphone HTTP response stopped/reaped the direct capture child;
status reported no child and no cleanup pending. The body had produced641,280
PCM bytes by closure; the client retained exactly640,000 for this finite test.
Owner-scoped release returned true, owner became null and preview inactive.
This does not claim that physical cleanup or electrical microphone mute is
proved by those acknowledgements; native capture status must be checked separately.

The resident desktop gateway was still running code from before the stream API.
While the camera was idle, `cammy-host.service` was restarted from the canonical
LAB checkout. Authenticated `/v1/audio/stream/status` through localhost8790 now
returns the real body state. Actual PCM forwarding through that resident gateway
is prepared for the next trial; this first PCM trial connected directly to Cammy.

## Human voice and resident desktop gateway — passed

After Adam's explicit ready-to-speak reply, the second trial ran35.015s of
video (168 monitor frames,167 changes), overlapping20.0s of microphone PCM
through the resident authenticated desktop gateway at localhost8790. It retained
640,000bytes,319,258 nonzero samples, RMS−33.88dBFS. First3200-byte PCM read was
0.310s after the request. Combined interface average was1.303Mb/s over35.558s.
P15 supplied only the three-beep start cue; it was not Cammy speaker output.

A local small.en recognizer processed the first eight seconds of incoming PCM
while both the stream and video receiver were running. It returned the wireless
voice-test sentence and the start of the next sentence in1.259s of recognition
work,11.460s after trial startup.50 video frames had arrived at that moment;
118 more arrived afterward. The eight-second prefix ended during the next
sentence, so the live result was partial. A separate recognition pass on the
full20s sample after the trial recovered the complete intended request for a
live conversation. These are intelligibility and concurrent-processing proofs,
not a finished streaming transcript/agent-response loop or end-to-end latency.
Raw speech/transcripts remain private. The demonstration waited for an8s prefix;
shorter rolling windows or in-session VAD are still needed for responsive turns.

## Real Stop and lease-expiry checks — passed

Two short streams through the resident gateway verified control behavior on
hardware. Explicit Stop acknowledged in15.3ms; no capture child/cleanup pending,
no owner and preview inactive were observed by43.3ms after the request. A2s
lease separately expired and likewise closed the stream/preview and reaped the
capture child. EOF was observed in both cases. These are control/software
lifecycle timings, not measured acoustic or physical microphone cutoff latency.

Already-buffered PCM remains readable after Stop:2560bytes in the explicit-Stop
sample and52,480bytes left unread until expiry in the other sample. This is
previously acquired audio, not a claim that it was recalled or erased. Consumers
must close/drop the stream and invalidate queued recognition results on Stop;
they must not accept buffered input merely because it can still be read.
Read-only USB confirmed native capture CLOSED after the voice test and after
these controls checks, with the same boot and native app. The shared profile
and detached guardian stay ready in RAM; forwarding is idle.
