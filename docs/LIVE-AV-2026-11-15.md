# First concurrent live video and understood microphone input

Real M105,2026-11-15. This is an entry proof for the
[live-media milestone](archive/LIVE-MEDIA-MILESTONE.md), not completion of Wi-Fi-only
audio, conversational latency, duplex output or sustained acceptance.

## Demonstrated outcome

During Adam's spoken test the PC received native video over home Wi-Fi and
microphone PCM over USB at the same time. No camera TF recording, shutter,
downloaded camera clip, application replacement or reboot was involved.

models is useful intelligibility evidence, not a reference-scored word-error rate.

## What unlocked live video

Initially the native8082/9999 services and the CammyOS portal listened, but8554
did not. Adam opened the camera's ordinary Wi-Fi screen. The native app then
created RTSP listeners bound to both the old home address and192.168.10.1.

The stock transition changed wlan0's address to192.168.10.1 while the radio
remained associated to the home network in managed mode. No hotspot appeared on
the PC scan. A newly created stock DHCP server was terminated using checked
PID/starttime/executable identity; the existing CammyOS DHCP client was signalled
to renew. Home address<camera-ip> returned. RTSP stayed available on home Wi-Fi.
No Wi-Fi credentials, network settings file, app executable or init script was
rewritten. The native UI initialization and IP recovery are not automated yet.

The authenticated CammyOS preview event connection still matters: a direct RTSP
attempt without it yielded no decoded frames. The working session holds the
control lease and ordinary9999/4016 preview session. Each test released that lease.

An independent eight-second RTSP/TCP packet observation completed DESCRIBE,
SETUP for both tracks and PLAY. It received193 video RTP packets,1,028,005bytes
in8.035s: about1.023Mb/s encoded RTP payload. This is one scene and excludes
TCP/IP/control overhead; it is not a worst-case total budget measurement.
The recording preset's4K/33Mb/s file rate does not describe this live preview.

## Why microphone sharing was necessary

The RTSP SDP advertises AAC8kHz mono, but neither TCP nor UDP reception decoded
audio. The packet observer saw no audio RTP packets. Meanwhile, after decoded
video began, the native physical microphone was RUNNING at16kHz mono S16_LE,
period960/buffer7680. This narrows the failure to the live audio publishing path;
an absent microphone driver or missing hardware signal is not the explanation.

Outside native preview, stock `arecord -D hw:0,0` streamed3s of physical PCM to
the PC:96,000bytes,first data0.254s,47,851nonzero samples. Opening that exclusive
hardware device during native preview is not a sharing solution.

The existing ALSA library supports `dsnoop`. An isolated configuration, visible
only to our own process, captured32,000samples with nonzero data. A subsequent
temporary shared profile let the native preview and our `arecord` process read
the same microphone concurrently. The profile kept playback configured for
hardware; camera-speaker behavior under this profile was not tested.

## Temporary configuration experiment and restoration

The successful test used only non-executable configuration data in an exclusive
root-owned RAM directory. The stock asound configuration was copied and extended
with a shared capture PCM and an asymmetric hardware-name mapping: playback to
hardware, capture to the shared microphone. This experimental mapping is broader
than a production profile should be; unrelated capture cards must be rejected
or passed through deliberately before shipping it.

Changing only `/etc/asound.conf` did not refresh the native application's cached
ALSA definitions. A host null-device experiment reproduced the cache behavior:
changing a hook-loaded include left the old configuration active; changing the
root configuration timestamp caused reloading. The successful camera trial also
bind-mounted a **byte-identical RAM copy** of `/usr/share/alsa/alsa.conf` with a
fresh timestamp. Both bind mounts were temporary. A separate timed guardian and
the host cleanup path restored the original views; no bytes on internal storage
were modified. Earlier unsuccessful configuration trials were also restored.

Final checks confirmed:

- Same boot, native PID/starttime, pinned app/init/libc hashes and watchdog owner.
- Original mount table and executable mappings restored.
- `/etc/asound.conf` SHA256 `1e4399ab…190edf9` and global ALSA configuration
  SHA256 `b2776093…de732d31` match their originals.
- Physical microphone closed after cleanup settled; test shared-memory objects
  gone, with only the original playback objects remaining.
- Home Wi-Fi address restored, control lease released, preview session stopped.
- Exclusive RAM configuration staging directory removed after the guardian ended.

The host null-device experiments are not hardware evidence. Conversely, these live
results do not validate every failure path of a production shared-capture manager.
No new camera executable, firmware or driver was installed. There were no direct
mixer commands that wrote values and no display-memory writes.

A follow-up stock preview reopened normally after restoration, with no trial
shared-memory key present, then closed its microphone again. A JPEG decoded
directly from live RTSP showed the monitor with this current chat's progress
messages. It was saved on the PC without a camera shutter or TF write. This
corroborates scene freshness, without a synchronized latency measurement.
Capture was closed again afterward.

## Remaining work, in execution order

1. Turn this prototype into an opt-in CammyOS shared-capture runtime profile,
   with exact-source checks, limited card/device scope, bounded cleanup and
   truthful status. Avoid requiring USB shell orchestration per session.
2. Add authenticated, owner-scoped live PCM transport over home Wi-Fi through
   the existing control plane. Stop, disconnect and lease loss must stop the
   owned stream. No arbitrary commands or unauthenticated audio port.
3. Feed short utterance/streaming windows into recognition; the20s verification
   window is too long for conversation. Prove a fresh visual cue and end-to-end
   audio/video latency, then complete the30-minute combined test.
4. Connect arbitrary speaker output without suspending video/microphone, then
   measure interruption, echo and double-talk. Recorded-video playback is not it.
5. Automate the native preview initialization/home-IP recovery and verify USB
   supplies power only. No TF update is ready solely from these host experiments.

Privacy limitation: native preview itself acquires the microphone even when its
RTSP audio publisher sends nothing. Stopping our PCM reader does not electrically
mute that native capture. Until a runtime mute/ownership policy is verified, do
not equate “agent audio stream off” with “physical microphone closed” during video.
The final test left both preview and microphone stopped.

## Reproducibility

`host/live_media_probe.py` receives live native media with authentication/lease
supervision and bounded buffers; default duration10s. It reports zero audio when
the native audio track sends nothing and does not fall back to another device.
Private receipts/configurations/commands and the human trial driver are in
`private/live-media/1794751936011747673/`; current task checkpoint is
`private/live-media/current.json`. These contain the exact config hashes,
before/after snapshots, RTP observation, speech cross-checks and restoration data.

Local verification:537 repository tests passed in125.025s, including eight new
live-receiver tests using synthetic realtime media, mock body/network state,
bounded SDP, cancellation/reaping and silent-audio refusal. No camera is used
by that suite. There is no new deployable TF release in this commit.
